# Unit Test Guide

本规范用于保证测试能够证明业务行为、定位回归原因，并在不同机器和执行顺序下稳定运行。测试数量和覆盖率只是辅助信号，不能替代有效断言。

## Test Boundaries

- 单元测试只加载被测对象及其直接协作者，不启动 Spring 上下文、网络端口、线程池或真实中间件。
- 自动配置、Bean 装配和应用启动属于集成测试，可以使用 Spring 测试上下文，但必须关闭或确定性替代 Nacos、Redis、Dubbo 等外部系统。
- 一个测试只描述一个可观察行为。多个断言可以共同证明该行为，但不要在同一方法中串联无关场景。
- 优先测试公共行为和状态变化，不通过反射、私有方法调用或内部调用次数固化实现细节。

## Structure And Naming

- 测试类使用 `<Subject>Test`；方法名使用 `conditionProducesOutcome`，直接表达条件和结果。
- 测试内容按 Arrange、Act、Assert 的阅读顺序组织；代码足够清楚时不要求添加形式化注释。
- 测试数据只保留与场景有关的差异。重复且复杂的对象创建可提取 fixture/builder，简单数据直接构造更清楚。
- 参数化测试用于同一规则的输入矩阵，不用循环隐藏某一组输入的失败位置。

## Assertions

- 每个测试必须通过状态断言、返回值断言、异常断言或关键交互验证证明结果；仅调用方法或仅断言“不抛异常”通常不足以证明业务正确。
- 断言具体业务结果，例如完整集合、状态、错误类型及关键字段，避免只断言非空、集合大小或 Mock 被调用。
- 集合有顺序语义时验证顺序；没有顺序语义时使用无序集合断言，不依赖偶然遍历顺序。
- 异常测试同时验证异常类型和稳定的业务信息或错误码，并验证失败后没有产生不应出现的状态或外部调用。
- 对持久化、消息投递、注册和迁移操作，应同时覆盖成功结果及关键副作用。

## Test Doubles

- 只 Mock 进程外适配器、时间、随机数和当前单元的直接依赖。实体、DTO、集合和值对象使用真实对象。
- `any()` 只能用于与当前行为无关的参数；路由键、用户 ID、消息内容、地址等关键参数使用精确值或 captor 验证。
- 不把生产代码改成仅便于 Mock 的结构，也不在生产源码中增加只供测试使用的 no-op/fake 实现。
- 验证交互时关注业务边界，不验证无意义的 getter、内部方法顺序或所有零碎调用。

## Determinism

- 禁止使用 `Thread.sleep` 等待异步结果或时间过期。时间通过 `Clock`/`LongSupplier` 注入，异步行为使用可控 executor、latch 或最终一致性断言工具。
- 测试不能依赖当前时间、随机端口之外的固定端口、执行顺序、共享静态状态或本机已有服务。
- 后端测试统一在 headless JVM 中运行；Excel、图片、字体等 Java2D 能力不得依赖本机桌面会话或注册 GUI 应用。
- 并发测试必须验证明确的不变量，并保证线程和 executor 在测试结束时关闭。
- 禁止用控制台输出代替断言；诊断信息应由断言失败消息提供。

## Required Scenario Depth

根据变更风险选择场景，不要求机械凑齐模板：

1. 正常路径及最终业务结果。
2. 无效、空值、边界值和不存在资源。
3. 失败、超时、重试及部分成功。
4. 幂等、重复请求和乱序事件。
5. 涉及共享状态时的并发竞争和所有权变化。
6. 修复缺陷时先增加能在修复前失败的回归测试。

## Review Checklist

- 测试名称能否在不阅读实现的情况下说明规则？
- 修改生产实现但保持行为不变时，测试是否仍然成立？
- 删除或反转关键业务逻辑时，测试是否会失败？
- 断言是否覆盖了真正有风险的结果和副作用？
- 测试是否存在时间、顺序、网络或机器性能依赖？
- Mock 是否越过了当前单元边界，或者掩盖了真实对象之间的协作？
- 测试失败信息能否直接定位被破坏的业务规则？

自动化门禁只检查低误报反模式。断言质量、场景深度和 Mock 边界由 Review 按本清单判断，不能为了机械规则制造形式化测试。
