# 技术设计文档规范

本文定义 im-chat 任务/需求技术设计文档的职责、结构、质量标准和生命周期。设计文档回答“为什么这样设计、系统将如何工作、失败时会怎样”；实现步骤和实时进度属于 execution plan，当前运行事实属于 Architecture/README，产品行为属于 product specification。

## 何时需要设计文档

出现下列任一情况时，应先在 `docs/design-docs` 创建设计，再写 execution plan 或生产代码：

- 跨模块、跨进程、跨数据所有权或公共协议变更。
- 新增一致性模型、状态机、持久化格式、基础设施依赖或安全边界。
- 存在两个以上真实可行方案，或决策难以回滚。
- 需要需求访谈、`grill`、brainstorming 才能确定行为。
- 会改变可靠性、容量、发布、迁移、回滚或运维方式。

局部、低风险、无行为变化的单文件维护可以不建设计文档；但只要问题的正确答案依赖一个需要长期保留的取舍，就不应只留在聊天记录、提交信息或 execution plan 中。

## 与其他文档的边界

| 文档 | 回答的问题 | 不应承载 |
|---|---|---|
| Product spec | 用户或业务期望什么行为 | 内部类拆分和实施进度 |
| Design doc | 为什么选择该方案，组件如何协作，错误和边界如何闭环 | 每个文件的施工 checkbox、当前执行状态 |
| Execution plan | 按什么顺序修改哪些文件，如何 RED/GREEN 和恢复 | 未获批准的新架构决策 |
| Architecture | 当前系统已经是什么形态 | 尚未实施的提案和阶段性进度 |
| README | 开发者如何理解、配置、运行和排障当前模块 | 历史方案比较和 Agent 工作流 |
| Reference guide | 多个任务复用的工程规范 | 单一需求的临时细节 |

设计实现完成后，应把稳定事实回写 Architecture/README；设计文档继续保留决策背景和取舍，不冒充当前运行手册。

## 生命周期与状态

文件名使用 `YYYY-MM-DD-<topic>-design.md`，并登记到 `docs/design-docs/index.md`。文首必须有可独立理解的状态行：

- `草案`：仍有开放问题，不能创建实施计划。
- `待 Review`：方案完整，等待用户批准或独立 Review。
- `已批准`：用户已确认且独立 Review 无 Blocker/Major，可以创建 execution plan。
- `已实施`：对应计划完成，稳定事实已同步到当前文档。
- `已取代`：由另一设计替代，必须链接新设计。
- `已撤回`：决定不实施，保留原因。

状态必须写出批准/Review 事实和适用范围，不能只写模糊的“完成”。实现开始后链接唯一 active execution plan；归档后更新为 completed 链接。

## 推荐结构

结构按读者决策路径组织，不按聊天时间线或作者思考顺序堆叠。小设计可合并章节，大设计应使用以下顺序：

1. **摘要**：用几段话说明问题、核心方案、关键取舍和发布边界，让评审者先看到结论。
2. **背景与问题**：描述当前事实、可复现缺口和现在处理的原因；区分已实现事实与目标状态。
3. **目标与非目标**：限定成功边界，主动写出容易被误解为本次范围的事项。
4. **已知事实与约束**：列出模块所有权、现有协议、数据来源、环境、安全、兼容和时间约束。
5. **方案概览**：给出系统图、核心数据流、状态所有权和最重要的不变量。
6. **详细设计**：按控制面、数据面、生命周期或端到端流程组织；每条主线写清模型、接口、状态转换、正常路径和失败路径。
7. **可靠性与安全**：说明超时、重试、幂等、并发、分区、恢复、授权、审计和资源上界。安全不能作为最终阶段外挂，必须随协议首次出现。
8. **运维与交付**：配置、可观测性、发布、迁移、回滚、容量和机器规格；不需要兼容或迁移时也要明确说明原因。
9. **验证策略**：把每个关键不变量映射到确定性测试、集成场景、故障注入和验收门槛。
10. **后续文档与执行**：列出需同步的 Architecture/README/规范，并在批准后链接 execution plan。
11. **附录**：行业依据、备选方案、库选型、完整决策记录和 Review 重点放在正文之后，供追溯而不打断主流程。

Broker 权威路由设计是复杂跨模块设计的结构示例：[Broker 权威集群状态与高可用路由切换设计](../design-docs/2026-09-19-broker-routing-consensus-design.md)。它不是要求所有设计复制同等篇幅；文档深度应随风险、状态空间和故障面增长。

## 内容标准

### 事实、假设与决策分开

- 当前代码事实必须能由代码、配置、Architecture 或测试定位。
- 尚未验证的性能、兼容性和库能力写成假设或 Spike 条件，不能写成事实。
- 最终决策说明采用什么、拒绝什么、为什么，以及对实现和运维的影响。
- 访谈中的 `A/B/C` 选择必须还原完整语义；仓库读者不应依赖聊天历史。

### 使用统一且边界清晰的术语

首次出现领域术语时定义“是什么”和“不是什么”。名称应表达所属上下文，例如 `RouteBroker` 比宽泛的 `owner` 更清楚。术语变更要全文一致，并同步公开 contract、图和决策记录。

### 用不变量约束设计

关键正确性应写成可反驳的陈述，例如“任意时刻最多一个 epoch 可以准入新的权威路由副作用”。不要把 admission、远端执行和完成混为一谈，也不要承诺系统实际无法证明的 exactly-once、零丢失或绝对可用。

每个不变量至少回答：

- 谁拥有该状态，谁可以修改。
- 线性化点或提交点在哪里。
- 超时、重试、乱序、重复、崩溃和恢复时如何保持。
- 哪个测试能让错误实现稳定失败。

### 接口描述行为而不是泄漏实现

接口示例用于固定职责、输入、结果和错误语义。应标明哪些名称/字段是 contract，哪些只是建议拆分。业务 Handler 不应直接暴露 Raft、数据库、Gossip entry 或具体客户端生命周期；deep module 应把复杂状态机藏在窄接口后。

### 完整描述正常与失败流程

流程至少覆盖：成功、明确拒绝、timeout/未知结果、重试、幂等、并发状态变化、进程重启和依赖不可用。图用于展示跨三个以上组件的关系或时序；图后仍需用文字解释权威状态、关键条件和错误出口。

### 安全、容量和发布是设计的一部分

- 新协议在首次引入时就定义身份、audience/scope、来源绑定、授权失败和审计边界。
- 容量结论必须绑定固定 workload、拓扑、阈值、重复次数、资源采样和三态结果；没有证据时写“待测”，不能猜机器配置。
- 明确是否存在已上线版本。尚未上线时不要制造旧协议兼容、双写或迁移代码；已上线时必须写混合版本窗口、数据迁移和回滚限制。

## 备选方案与行业依据

至少比较两个真实可行方案；如果只有一个合理方案，说明其他方案为何不成立。每个方案写清收益、代价、失败模式和适用条件，不能为了衬托推荐方案而设置明显不可用的陪衬选项。

涉及共识、加密、协议标准、第三方库能力或行业实践时，优先引用官方文档、标准或论文，并记录版本。外部资料支持的是事实和先例，不替代对本仓库约束的推理。研究材料最终应收敛到设计附录；没有独立复用价值时不另建竞争事实源。

## 决策记录

文末维护稳定 ID 的决策表：

| ID | 来源/问题 | 最终决策 | 理由与影响 |
|---|---|---|---|
| D1 | 要解决的具体分歧 | 脱离会话也能理解的完整选择 | 取舍、边界、后续约束 |

正文负责让读者理解系统，决策表负责追溯。不要把所有解释都塞进表格，也不要在正文和附录复制两套相互漂移的规范。

## 验证与 Review

验证策略必须覆盖设计中的每个高风险属性：算法 golden vector、状态机转换、并发线性化点、故障注入、安全拒绝、资源上界和发布/迁移契约。使用明确阈值和失败分类，不写“充分测试”“保证高可用”之类不可执行措辞。

设计进入 `已批准` 前必须完成两类确认：

1. 用户/需求方确认目标、范围和主要取舍。
2. 独立上下文 Review 对照当前代码、Architecture 和需求检查 Blocker/Major。

Review 采用 findings-first：每项包含位置、风险和修订建议，结论使用 `Approved`、`Revise` 或 `Block`。`Revise/Block` 的问题逐项修订后重新 Review；Review 轮次和最终结论写入状态或附录。具体代码 Review 输出规范见 [Code Review Guide](CODE_REVIEW_GUIDE.md)。

## 从设计交接到实施

命中本文“何时需要设计文档”触发条件的工作，只有设计 `已批准` 后才能创建 execution plan。无需设计文档的工作可以由已批准 Product spec 或 `docs/PLANS.md` 允许的其他事实源直接进入计划。交接时检查：

- 每个重要组件、协议和状态机都有明确所属任务。
- 安全实现与协议首次引入处于同一任务，不延迟到最终集成。
- 每个不变量都有 RED fixture、最小实现和 GREEN 命令。
- Spike 覆盖设计列出的全部退出条件，缺少目标平台证据时任务应 blocked。
- 容量、迁移、改名和真实拓扑验证有准确命令、报告 schema、freshness 和失败恢复。
- 最终任务不能用“存在证据缺口”冒充 passing；未满足验收标准必须保持 blocked。

execution plan 可以补充准确文件、类名和命令，但不能静默改变批准设计。发现新取舍时先更新设计并重新 Review，再调整计划。

## 提交前检查清单

- [ ] 状态、主题、范围和读者无需聊天上下文即可理解。
- [ ] 当前事实、假设、目标状态和最终决策没有混写。
- [ ] 目标、非目标、所有权和关键术语明确。
- [ ] 正常流程、失败流程、并发、超时、重试、幂等和恢复闭环。
- [ ] 安全、可观测性、容量、发布、迁移和回滚适用项已覆盖。
- [ ] 备选方案是真实可行选项，推荐理由包含缺点。
- [ ] 关键不变量均能映射到确定性验证。
- [ ] 决策记录还原完整语义，未只保留访谈选项字母。
- [ ] 独立 Review 无未处理 Blocker/Major。
- [ ] index 状态、execution plan 链接和后续事实文档同步要求准确。
