# Git Guide

本规范是仓库 Git 操作与提交信息的唯一完整约定，开发者和 AI 共同遵循。README 只保留摘要，`AGENTS.md` 负责规定 AI 的执行入口。

## 提交权限

- 只有用户明确要求提交时，AI 才能执行 `git add` 和 `git commit`；完成代码或验证不等于获得提交授权。
- 用户要求暂不提交时，不得通过计划、脚本或自动流程间接创建提交。
- 未经用户明确要求，不执行 push、rebase、merge、reset、checkout 丢弃修改或历史改写。

## 提交边界

提交前必须执行 `git status --short` 和检查实际 diff，区分当前任务修改与工作区中已有的用户修改。

- 一个提交只表达一个可独立审查和回退的主题。
- 不得为了得到干净工作区而还原、覆盖或提交无关修改。
- 使用精确路径执行 `git add`；只有确认全部变更属于同一主题时才使用 `git add -A`。
- 文件移动优先使用 `git mv`，保留历史可读性。
- 格式化、重命名和机械生成变化应服务于当前主题；大范围机械变更应与行为修改分开，除非二者无法独立成立。
- 跨模块改动可以放在同一提交中，但正文必须说明职责边界、调用链路或数据所有权为何需要一起变化。

## 拉取与分支整合

- 当前本地分支同步其对应远程上游时使用 rebase，例如 `git pull --rebase`，或先执行 `git fetch` 再执行 `git rebase <upstream>`，保持当前分支提交历史线性。
- 将其他功能分支、修复分支或发布分支的代码整合到当前分支时使用 `git merge <branch>`，保留分支整合事实；不要用 rebase 代替跨分支合并。
- 不对已经推送并由他人使用的共享提交执行 rebase，也不通过强制推送改写共享历史。发现上游历史冲突时先停止并确认协作方处理方式。
- 上述命令不会扩大 AI 的操作权限；未经用户明确要求，AI 仍不得执行 pull、fetch、rebase、merge 或 push。

## 提交前验证

提交前至少执行：

```bash
./scripts/verify.sh full
git diff --check
```

同时确认：

- 实际暂存内容与准备描述的提交主题一致；
- 没有生成目录、IDE 元数据、日志、凭证、Token 或本地环境值；
- 新增文件已纳入检查，删除和重命名符合预期；
- 验证失败时不提交，不通过弱化规则、删除测试或扩大排除范围绕过门禁。

验证命令和结果应在工作说明中报告。只有测试、门禁或验证设施本身属于本次改动时，才将其写入提交正文；不要为每次普通提交机械追加“测试通过”。

## 提交信息

提交信息沿用仓库 `c0005f6` 等提交形成的中文标题和编号正文格式：

```text
<中文动词开头的简洁标题>

1. <第一组完整改动，说明新增或调整的核心能力及目的>

2. <第二组完整改动，说明模块结构、调用边界或配置变化>

3. <第三组完整改动，说明兼容处理、测试、文档或清理>
```

具体要求：

1. 标题使用“新增、优化、调整、修复、拆分、清理、完善”等动词开头，概括提交目的，不罗列文件名，结尾不加标点。
2. 标题与正文之间保留一个空行；正文使用连续数字编号，不使用无序列表。
3. 每条正文描述一个完整改动维度，优先按照“核心能力、架构与配置、验证与清理”的顺序组织，不按文件逐项罗列。
4. 正文解释改了什么以及为什么一起改，避免“调整代码”“优化逻辑”“补充测试”等缺少对象和行为的信息。
5. 涉及跨模块重构时，说明新的职责边界、调用链路和数据所有权；涉及运行行为时，说明默认配置、兼容策略和失败处理。
6. 编号数量由实际改动维度决定，不要求固定三条；不要拆分同一事实来凑编号。
7. 提交信息只描述当前提交中实际暂存的内容，不描述计划、未完成工作或工作区中的其他修改。

## 示例

符合规范：

```text
优化仓储缓存与配置管理

1. 新增仓储缓存代理与 JetCache 远程缓存配置，补充缓存名称常量和领域缓存值序列化支持

2. 拆分基础设施 Bean 配置，整理启动与仓储缓存集成测试包结构，抽取 SpringBootTest 测试注解

3. 清理未使用的 CQRS 模型和仓储依赖，补充缓存代理单元测试与启动集成测试
```

不符合规范：

```text
修改代码

- 修改 BrokerStateStore.java
- 修改 README.md
- 测试通过
```

该示例的问题是标题没有表达目的，正文按文件罗列，且“测试通过”不是改动内容。

## AI 执行清单

收到明确提交请求后，AI 按以下顺序执行：

1. 阅读本规范和当前范围内的 `AGENTS.md`。
2. 检查工作区、暂存区和最近提交风格，识别非本次任务修改。
3. 完成全量验证和 diff 检查。
4. 仅暂存属于目标提交的文件，并复核 staged diff。
5. 根据 staged diff 编写中文标题和编号正文。
6. 创建提交后报告 commit id、标题、纳入范围和验证结果。

无法可靠区分修改归属、验证未通过或提交范围与用户要求冲突时，不创建提交，并明确说明阻塞原因。
