# 群聊会话补偿与通知对象设计

> 状态：草案。已确认从 Broker 成员流程收口中拆出，先做独立设计；候选方案未获批准，未创建实施计划或修改生产行为。

## 摘要

本设计拆开两个问题：Social 的群变更提交后，Message 如何补齐会话；Message 已提交消息副本后，如何确定即时通知对象。候选方案分别是持久记录待投递的群变更，以及以已提交副本限定通知候选人。前者保证变更可恢复，后者防止通知对象因读取时点变化而扩大；两者均不改变 Social 的成员权威或 Message 的消息所有权。

## 当前行为与风险

- `GroupAppService` 在创建、解散、加入、退出和移除成员的变更路径中，用 `AfterTransactionCommitTemplate` 调用 Message Facade。模板在有事务同步时注册进程内 `afterCommit`，否则立即执行；没有持久待办。提交后进程退出或 RPC 失败时，Message 可能缺少会话或保留旧会话。调用报错也不能反推出 Social 未提交。
- `GroupMessageAppService` 发消息时根据当次成员及会话为各接收人写入收件箱副本，提交后发布事件。`onMessageSent` 和 `onMessageRevoked` 调用 `findRecipientChats`，重新读取 Social 的当前成员。新成员可能进入一条没有为其写入副本的通知；已退出成员可能错过已写入副本对应的通知；一个成员缺会话可能中断接收人解析。
- [Message Architecture](../../im-service/im-message/ARCHITECTURE.md) 区分 MySQL 持久事实与在线通知。`ReceiptTask` 负责 Message 自己的在线投递，不保证 Social 到 Message 的群变更交接。

## 目标与非目标

- 群变更提交后可判定 Message 投影是否已跟上，并能恢复重复、超时和进程重启造成的交接中断。
- 发送与撤回通知不覆盖没有对应已提交副本的用户；明确退出、被移除和重新加入时的投递与可见性规则。
- 不引入跨库事务，不让 Message 反写 Social 成员，不改变 Broker、Gateway、私聊或客户端 ACK 协议。不承诺实时投递与成员变更之间的强原子性。

## 候选方案

### A. Social 群变更交接

建议在 Social 的业务事务内持久化待投递记录（outbox），与群成员变更同提交、同回滚。记录携带稳定事件 ID、群 ID、同群有序版本及最小变更事实。提交后的唤醒仅用于降低延迟；后台按有界批次经内部 Facade 投递，重启从未确认记录继续。Message 在自己的事务内更新会话投影并记录已应用位置；确认丢失时，重放已应用事件应返回幂等成功。必须定义版本缺口、同版本内容冲突和永久失败的隔离与人工修复路径；不可跳过缺口后仍声称同群已同步。

备选是定期从 Social 权威状态对账，再修复 Message 会话投影。它能覆盖历史缺口，但需要稳定分页、扫描水位与处理已删除群的办法，且可能抹去退群后重入等中间语义。是否以对账作为首版方案或仅作历史修复，取决于是否必须保留变更顺序以及预期扫描成本。

### B. Message 通知对象

建议从发送或撤回事务涉及的已提交收件箱副本冻结通知候选集，使用 Message 自己的持久事实或随事务记录的投递目标；不从当前群成员扩充候选集。发送和撤回分别沿用已有的发送人过滤及通知规则。在线通知不是读权限；历史副本可见性仍由现有授权约束，且退出后的主动通知是否需要抑制，应由产品决定。若要求抑制，则只在冻结集合上做当前资格过滤，并明确资格查询失败的重试或抑制规则；异步检查不能承诺消除检查后到送达前的竞态。新加入或重新加入不能凭当前成员身份扩大历史通知集合。

备选是保留当前成员查询，但与已提交副本取交集。这能减少对已退出用户的即时通知，不会发送没有副本的事件；代价是每次投递依赖 Social 的实时可用性，且需明确延迟撤回、重试及重新加入时的资格。仅查当前成员、不核对副本不能满足候选目标。

## 可靠性、安全与交付

- Social 是群成员权威，Message 是会话投影与收件箱权威；跨服务仅传必要事实，不暴露跨库访问或新增公网入口。受信调用身份、事件格式和授权失败语义需在批准前具体化。
- 投递批量、并发、退避、保留期和监控阈值待容量及故障验证。监控未确认最老年龄、重试、缺口及永久失败；不以群或用户标识作指标标签，不输出消息正文。
- 上线前先确认已有部署，以及是否需要消费者先升级、历史会话对账和混合版本窗口。回滚不能丢弃尚未确认的交接记录，也不能把切换通知规则当作历史补发。当前没有迁移或实施授权。

## 验证策略

| 场景 | 验收证据 |
|---|---|
| Social 回滚；提交后、投递前退出 | 回滚无待投递事实；提交记录在进程重启后仍可经真实 Facade 投递 |
| Message 已提交、确认丢失；重复、乱序、版本缺口 | 不重复变更投影，不回滚已应用版本；缺口或冲突可见且可恢复 |
| Message 长时间不可用或已有会话偏差 | 重试有界且阻塞可观测；恢复后按批准的顺序或对账规则收敛 |
| 提交与通知之间加入、退出或重新加入 | 对比真实收件箱副本和发送、撤回通知；无副本用户从未进入通知，退出行为符合最终批准的规则 |
| 单个目标缺会话或通知失败 | 按最终约定隔离、重试或报告，不扩大候选集，不回滚已提交消息 |

聚焦事务和幂等验证使用专属 MySQL；集成验证走 Social／Message Facade，按场景区分真实依赖与替身。实施后执行模块、架构、完整门禁和独立 Review。同步两模块 README、Message Architecture 和 Reliability 的已实现事实。
