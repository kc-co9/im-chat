# 收尾流程收口与验收去重提案

> 状态：用户已批准保留／延期边界，[精简实施设计](2026-10-22-closeout-process-simplification-implementation-design.md)已获独立设计批准并在实施中。S1/S2 已完成聚焦验证，S3 文档与真实 full 验收尚未完成。下文审计及候选方案保留为决策历史，不表示旧平台仍可用，也不将旧失败升级为 passing。

## 审计结论

原A5代码与文档已有多轮完整成功，但收尾又引入约1600行新阶段/归档helper及fixture，叠加约240行真实HA进程监督，形成独立验证项目。当前full的 --resume仍从头执行所有阶段，不提供成功阶段跳过，因此并未实现恢复省时。

成功样本chain-20261021T110928Z-10593-4493：full1322秒，其中scripts614秒、HA316秒。父自测占约46%；quick与full都运行一次父自测。最近一轮quick774秒，随后单独architecture134秒、startup231秒、behavior49秒、e2e46秒，之后full再次执行相同测试。这些是历史测量，不是当前fresh证明。

默认Maven verify包含Architecture、startup-smoke、realtime-behavior、E2E测试；专用wrapper还检查startup完整映射/Nacos隔离、tag和非零执行数、运行日志。去重不能删掉这些证明。真实容器拓扑、故障恢复和清理不能由JUnit代替。

## 推荐收口

### 保留必要修复

- 缓存测试分离不可变/过期语义与容量有界收敛，保留容量2及无限容量反证。
- load-test ps/wait竞争修复、原子失败传播和确定性采样算法检查。
- HA Engine有界前检、命令边界、单次有界清理及本次进程组所有权保护；不退回无前检和0.2秒强杀清理的旧实现。
- 原HEAD/完整fingerprint冻结与独立质量审查；不靠伪造fresh解决重复。

### 延期非必要新平台功能

推荐将固定阶段chain/attempt、--through/--resume、全模式journal/supersession、archive prepare/verify发布状态机从A5交付前置中移出。撤回须作为完整功能闭包：verify入口、report/handoff消费者、fixture接线、规范同步一起选择性修改。只删helper或整文件git restore均禁止。原实现与证据先保留到可追溯归档，设计/计划标延期，不标已交付成功。

这个选择会失去当前archive-audit关闭特权，必须同步其政策，不保留无实现支撑的例外。任何替代状态审计方案都需另有明确批准，不能偷偷忽略文档指纹。此项是用户需确认的取舍，不因已投入代码而强行保留。

## 唯一验收合同目标

最终成本目标是同一冻结实现下：**父自测一次、完整Java reactor一次、真实HA一次**，最后独立Review与当前治理检查。quick是迭代入口，不在同输入最终full前后重复执行；quick之后不再额外执行同一architecture。范围内源码/依赖变化仍使相关证据失效。

保留以下证明，不能仅按命令名字认定覆盖：

| 验收责任 | 计划的唯一执行/证明来源 |
|---|---|
| Harness正反fixture | 父自测一次 |
| Java全部断言/architecture/启动/行为/E2E | 完整reactor一次，保存本轮报告，拒绝零测试与失败 |
| startup映射/Nacos隔离、behavior/e2e tag及专用运行证明 | 从同轮报告做等价校验；实现前不删除现行wrapper要求 |
| 容器HA拓扑/故障恢复/清理 | 一次真实HA，25场景和空ledger条件不变；聚焦Java证据可引用同轮reactor，但必须匹配实际selector/报告输入，不使用旧target猜测 |
| 质量/状态/归档引用 | 独立Review与廉价治理检查，归档前先模拟引用；非状态文档必须在冻结前完成 |

上述等价校验已在 S1/S2 接通并完成聚焦验证，尚未经新流程真实 full 验收，不宣称已有实测收益。原full先HA后Java，使后面的Java失败浪费已运行的容器成本；建议顺序为静态/自测→Java→HA，先早暴露低成本失败。容器完成前仍不能overall passing，失败不自动重试。

## 执行纪律

1. 每个任务先固定范围和唯一验收清单，区分实施通过、运行环境问题、历史风险及明确延期。A5与Harness项目不得互为无限前置。
2. 同一最终输入只运行清单一次；失败只做该层诊断和聚焦复核。新证据不足时保持blocked，不下一轮full碰运气。
3. 冻结前盘点全部Git-visible引用、状态索引、磁盘峰值与Engine响应。冻结后禁止补README/设计或便利改名；必要改变明确重新打开受影响证据。
4. fixture算法断言用固定时间/可控调度；真实进程测试保留握手、退出码、所有权和有限防挂，不把宿主启动精度当算法正确性。审查同类问题一次盘点，不等每轮末尾才发现。
5. 单次外层执行预算与阶段期限分开，原失败码保留。环境恢复先独立验证，不借此重做全仓。
6. 状态记录只有一个当前恢复入口，历次记录明确标历史，不再不断追加多个“优先”入口。机器数值由Harness记录拥有。

## 备选与建议

- **推荐：先确认收口边界，保留战术修复、延期链式平台，建立去重验收合同。** 减少维护面，但需要准确回撤调用/fixture/政策并保护混合工作树，不能立即执行大范围restore。
- 最少当下编辑：保留全部现有功能，停止扩展，只去掉人为重复调用。可立即减少quick后architecture这类冗余，但长期复杂度和full内重复仍在。
- 不推荐再设计第三套缓存/归档框架；会延续当前成本问题。

当前按已批准的精简实施设计完成 S3 政策同步与真实 full 验收；上述备选仅为决策历史，不重新要求用户选择，也不运行 full 来批准流程方案。
